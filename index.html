    Debug a flaky save test

    A profile saves in the browser, but the automation sometimes reads its status too early. Diagnose the failure, fix the test, and explain how you would verify your change in CI.

    Reproduce the failure

    The starter test passes when the demo responds in 20 ms and fails when it responds in 650 ms. Both delays use the same fixture and successful save flow.

    await page.getByRole("button", { name: "Save profile" }).click();
await page.waitForTimeout(100);
const status = page.getByRole("status");
expect(await status.textContent()).toBe("Profile saved");
    Read the failure trace excerpt 
    Expected: "Profile saved"
Received: "Saving…"

  await page.waitForTimeout(100);
  const status = page.getByRole("status");
> expect(await status.textContent()).toBe("Profile saved");

    Your task

    1. Explain what the snapshot of the status tells you about the failure.
    2. Replace the fixed wait and one-time read with an assertion that waits for the saved status.
    3. Check that the change passes with both response times. Explain how you would confirm the fix under the original CI conditions.
    Hint

    Keep the status locator and ask Playwright to retry the expected text on that locator. A successful click and a completed save are separate events.

    Reference solution and verification 
    await expect(page.getByRole("status")).toHaveText("Profile saved");

    This retries the locator assertion until the status changes or the assertion times out. Run both response-time cases repeatedly with retries disabled. In CI, use the original browser, runner, and worker settings, and inspect the failure trace if either case still fails.

    Catch an order that never saved

    The create-order endpoint returns 201 and an order ID. Standard orders can be retrieved immediately. Express orders return the same success response, but the record is missing.

    Your deliverable

    1. Write a test that checks the creation response and retrieves the order by the returned ID.
    2. Assert the stored item, quantity, and delivery method. Run the same check for standard and express orders.
    3. Record which call disagrees with the contract and the observed status.
    Hint

    The create response can echo fields even when the write is lost. Make a separate GET request.

    Reference solution

    Assert 201 and the response fields on POST, then assert 200 and matching values on GET. The express GET returns 404 on the buggy fixture. Run the same tests against the fixed fixture to show that both cases pass.

    Make a checkout release recommendation

    You have 45 minutes before a checkout release. A new retry button appears after payment times out. The requirement calls for at most one charge and one confirmed order per checkout. The payment sandbox can simulate a decline or a late approval.

    Your deliverable

    1. Write three test cases with preconditions, actions, and observable expected results.
    2. Assume a retry succeeded once after a decline, but the late-approval case could not be run. Write a two-sentence release recommendation that names the gap, its impact, and the evidence you need.
    3. Choose one check to automate and explain which layer should own it.
    Hint

    A successful screen can hide a duplicate charge. List what you would verify in the order record and payment sandbox, and identify which outcome must stay consistent after retry.

    Example test plan and release recommendation
    • Happy path. Submit once with an approving payment. Verify one charge and one confirmed order, with the same amount in the confirmation and payment record.
    • Decline and retry. Decline the first attempt, confirm that it creates no charge or confirmed order, then retry with approval and verify exactly one of each.
    • Late approval. Delay the first approval past the UI timeout and select Retry. Reconcile both attempts after the late response and verify at most one charge and one confirmed order.

    I’d recommend holding the retry change or keeping it disabled until we verify the late-approval case because a delayed first response could lead to duplicate charges. I’d ask the release owner to revisit that decision after the sandbox shows one charge and one order for the original checkout.

    Automate the duplicate-charge check at the service boundary with a controlled payment sandbox. Keep a UI check for whether the retry controls and status messages make sense to the customer.
